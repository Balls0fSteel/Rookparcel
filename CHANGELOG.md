## 2026-11-17_092503_1794903903: Version 1.2.64: peers again after a file is turned on; Files tab sort; a visible unfocused selection (D78)

- **"Downloading" with no peers after turning a file on (owner):** two delays, both reproduced. The seeds `on_finished` closed as redundant were stamped as just connected, so each waited out `min_reconnect_time` (60 s, longer after failures) before it was a candidate again; libtorrent 2.0's `resume_download` has the same gap. And nothing re-announced: the next tracker announce could be an interval (about 30 min) away, asked with `numwant` 0 when the torrent had many peers. A theory that trackers saw left=0 was ruled out (a skipped file keeps left above 0). New `Engine::resume_download` for the finished-to-downloading change: reaps pending closes, forgets every known peer's last connection (as on leaving upload mode), asks each tracker again as soon as its `min interval` allows (`TrackerEntry::announce_soon`, not for failing or busy trackers; event none), prompts the DHT and LSD and connects at once. A stopped torrent that becomes unfinished now asks for an auto-manage pass. New swarm tests (reconnect with a 3,600 s reconnect delay; a re-announce with left>0 that finds a seed only the tracker knows) failed before and pass; the old skip test lost its second-seed workaround. Wire format unchanged, so `PEER_ID_PREFIX` stays. Still as in libtorrent: Force Re-Check and pause/resume leave peers in the 60 s delay.
- **Files tab sort (Win32, owner):** header clicks sort by any column (names, sizes and pieces ascending first; Done, % and Priority descending first), a second click reverses, a third returns to the torrent's order; the tree sorts each folder, folders first; kept as `ui.files_sort`. Rows moved by progress or priorities keep their selection. The owner's offer of a limit or a progress dialog was measured away: 100,000 files sort in 1-66 ms in a release build (`sorting_a_hundred_thousand_files`, ignored by default). GTK and macOS sort no detail table yet (BACKLOG); the Web UI already sorted Files.
- **Unfocused selection (Win32, owner):** after Alt+Tab a selected row was drawn in the button face (0xF0F0F0), one step from the shaded rows (0xEFEFEF), so it vanished on them. Now the highlight mixed into the window colour (30 % light, 70 % dark) under the window's text; High Contrast keeps the highlight. Pictured light and dark on the hidden desktop.
- **Validation:** frontend 451 tests, Win32 172 (one thread), core lib and every core test binary (swarm 62), clippy and rustfmt clean on the changed crates.

## 2026-11-16_213625_1794861385: Version 1.2.63: the security review of 1.2.58-1.2.62 and its fixes

- **Review:** the per-release review over `v1.2.57..HEAD` by three read-only reviewers (daemon and Web UI, engine and shared code, desktop programs); recorded in SECURITY-REVIEW.md "Release 1.2.63". Nothing critical or high. The daemon was probed live on loopback (403, 405, Origin and Host on every new endpoint); the `ip_filter` fuzz target ran 90 s (982,822 runs, CIDR reached, no findings).
- **Fixed, D77 (Append .!ut):**
  - A torrent with both `x` and `x.!ut` (option on), `x` and `X.!UT` (Windows) or `x` and `x.!qB` (option off, the default) could store two of its files at one path, one overwriting the other (medium, reproduced; a recheck recovered it). A file now never takes a suffixed name that is another file or folder of the torrent (compared case-folded everywhere); the start-up look, renames and the part-file export never take another file's path. Regression tests for the four cases and a randomised property test.
  - Remove and Delete Data deleted a same-named `.!ut` / `.!qB` file the torrent never wrote. Now such a file goes only when it holds this torrent's data (written here, a checked piece, pieces or blocks the engine has); otherwise it is kept and the Logger says so. An adopted µTorrent or qBittorrent partial that was never verified is therefore kept too.
- **Fixed, daemon:** tag calls do their name work once per request before the lock (an 80 KB request against 2,000 torrents held it 11.7 s); `GET /pa/prefs` sends the block-list and tracker-list addresses without credentials, query or fragment (none when hosted; sent back unchanged they keep the stored value); excluded names are matched outside the lock with a new bit-parallel matcher giving the old results; exported `.torrent` bytes are cached only while an export waits.
- **Fixed, block list (D75):** a new address keeps the old address's copy until its own list is saved, so Update Now then Cancel, or a failed fetch, no longer leaves the filter empty; at start a copy of another address is not loaded and the Logger says no list is in force yet. The Windows program's Update Now on unapplied fields is a trial that changes nothing until OK or Apply.
- **Fixed, desktop:** the Windows program opens no context menu while locked except the tray's; GTK refuses every window and application action while locked except Quit and Lock, also over the session D-Bus (checked live on the Xubuntu VM with `gdbus`; open since the 1.2.54 review); the Mac's Tags ▸ and Label ▸ items name the list the menu was built from.
- **Fixed, small:** a server's HTTP reason phrase and redirect host are cut to 100 / 300 characters without control or direction characters in status lines and the Logger; the block-list address's redaction no longer shows part of a password containing `?` or `/`; export file names avoid `COM¹`-style and `CONIN$` / `CONOUT$` device names.
- **Left open by decision:** BACKLOG "Security review 1.2.63" (a block list is trusted whole, no Mark-of-the-Web, D66's tracker list still drops its copy on an address change, magnet exclusions under the lock, `failure reason` text, unfuzzed parsers, and the rest).
- **Checked on the combined tree after the bump:** fmt clean; clippy `-D warnings` clean for core, frontend, nox and Win32, both Mac cross-lints and GTK's; the fuzz workspace checks. Tests: core 1,146 (973 unit, 171 integration, 2 doc), frontend 449 and 8 in its test files (the settings fixtures pass unchanged, so no 1.2.63 fixture), Win32 170 (one thread), nox 240, the Mac's portable 24; all passing. ## 2026-11-16_193121_1794853881: Version 1.2.62: Append .!ut to incomplete files (D77); feature wave 4

- **Asked for (owner, 2026-11-16):** wave 4, µTorrent's "Append .!ut to incomplete files", if it could be made reliable. Preferences > General > When Downloading in the three GUIs and the Web UI (`append_incomplete_ext`, `lt.append_incomplete_ext`, shim `incomplete_files_ext`), off by default.
- **What it does:** a file still downloading is `name.!ut` and gets its name once every piece it overlaps has passed; toggling renames running torrents' files at once, stopped ones' at their start. Not for pad, empty or symlinked files or names over 241 bytes; a user-renamed file carries it after the new name. Nothing is stored: the names follow from the pieces, so a crash between a rename and the next resume save heals at the next start.
- **Adoption, on or off:** a file missing under its expected name is looked for as plain, `.!ut`, `.!qB`, so µTorrent's and qBittorrent's partials are used (then named as the pieces call for). Relocate of a file not on disk and Set Download Location look the same way at the new place; a qBittorrent import takes `.!qB` off its mapped names.
- **Failed renames:** the file stays in use under its present name, one Logger line. A sharing or permission failure is retried at the next completed file, stop, resume save (30 s) and start; a name taken by another file is never overwritten and not retried on a timer. On Unix a crash between link and unlink is finished at the next names job.
- **Engine:** `Alert::FileCompleted` (category `FILE_PROGRESS`, off by default; every program's Logger shows it when asked). `TorrentFinished` waits for the last renames. Remote protocol 19 to 20: update a remote window and its daemon together. The peer ID stays `-RP1014-` (no wire change).
- **Review** by a separate subagent; F1-F7 fixed with regression tests:
  - F1: a start waits for the renames its previous storage still has queued (Force Re-Check, Pause/Resume, queue rotation right after a file completes); else the new check could find a name the file was losing and download it again beside the complete one.
  - F2: Relocate of a file not on disk onto an existing plain file uses it (it looked for `<to>.!ut`).
  - F3: `files_completed_by` without the quadratic search, skipped unless the alert or names want it; `set_names` builds paths only for files that change; names jobs coalesced to one in flight per storage (a burst of completed files costs two barriers).
  - F4: only sharing/permission failures retried; Unix same-file case; Set Download Location's replace mode replaces a plain `x` with `x.!ut` again, Don't Replace and Fail If Exist see `x` under any name.
  - F5: qBittorrent's mapped `.!qB` names stripped; the µTorrent importer needs nothing (its `targets` hold plain names).
  - F6: the start-up probe's look at a file serves the resume check (one stat per present file, as before D77).
  - F7: no `.!ut` where `.pa-export` after it would pass 255 bytes.
- **Checked after the fixes and the bump:** fmt clean; clippy `-D warnings` clean for core, frontend, nox and Win32, both Mac cross-lints and GTK's. Windows: core 1,134 (961 unit, 171 integration, 2 doc), then the names tests (18), the D77 swarm tests (12) and rename/move (14) twice more; frontend 444 and 8 in its test files (the 1.2.62 settings fixture among them); Win32 168 (one thread); nox 235; the Mac's portable 23; all passing.
