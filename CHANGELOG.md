## 2026-11-14_154940_1794667780: Version 1.2.53: GTK hand checks 30 and 14; a second SIGTERM while closing

- **Asked for:** run the two GTK fixes of [BUGHUNT-2026-11-05.md](docs/BUGHUNT-2026-11-05.md) that were compiled but never run (30 and 14). Both were run on the Xubuntu VM (1.2.52 debug build, Xvfb with no window manager, a private D-Bus, scratch settings and library), each also against a build with its fix disabled.
- **30, Create's Cancel during the last piece: passes.** An 18 MiB folder at 16 MiB pieces (two pieces, hybrid, "Start seeding" on), new content each trial; the Create window closed by `WM_DELETE_WINDOW` a set time after Return in the save dialog; an inotify log of the folder, and the library's `metadata.pack` for adds. The save dialog hands the file over about 0.5 s after Return (GTK ignores a close while it is up), hashing takes about 0.44 s more. Of 26 trials, 13 hit the race order: the worker wrote the .torrent 5-73 ms before the close, the app removed it 1-46 ms after, nothing was added. 3 were cancelled before the last piece; 10 finished before the close came and were added, as they should be (the list showed 10). With the guard disabled, 11 of 14 trials at the same delays kept the file and added the torrent.
- **14, a quit during the closing window: passes.** `tools/closing-test` with one 1.2 GB torrent moving to the throttled loop-mounted target. The main window was closed 2 s after the move began; SIGTERM followed 3 s later, at 129 of 1200 MB. The closing window stayed ("Waiting for files to finish moving") and the process ended 45 s later, after the whole file had landed and `resume.log` had been written. A restart lists the torrent seeding from the new folder without a recheck. With `quit_app`'s `CLOSING` test disabled, the process was gone 1 s after the signal, the copy stopped at 120 MiB, the source stayed and nothing was saved: the original fault.
- **Found and fixed:** after a close started by SIGTERM (or Ctrl+C), a second identical signal still killed the process mid-save. On the VM it was gone 1 s later, at 128 MiB, with nothing saved. Cause: the handler returned `Break`, and GLib puts the default action back once a signal's last handler is removed. Now `watch_quit_signals` keeps both handlers installed; `quit_app` already returns while the closing window waits. A forced exit is still SIGKILL or the closing window's Quit Now. Test `every_quit_signal_is_handled` sends SIGTERM to its own process three times; with `Break` the second one ends the test run. 1.2.53 on the VM: both sequences (close then SIGTERM, SIGTERM twice) stayed up 44-46 s, finished the copy and saved.
- **Not run:** the tray's Exit (no tray on a private bus), which calls the same `quit_app`.
- **Validation:** on the VM, `cargo test -p rookparcel-gtk` 23 passed. From Windows, clippy 1.100 `-D warnings` on the GTK crate (Linux target, all targets) and rustfmt are clean.

## 2026-11-14_150056_1794664856: Version 1.2.52: the bug hunt's inherited quirks; hand check 26

- **Asked by the owner:** what is left of [BUGHUNT-2026-11-05.md](docs/BUGHUNT-2026-11-05.md). Every finding was already closed. What remained: its three "inherited quirks" and two hand checks (26, 30).
- **A v2-only single file from a web seed:** a v2 file is padded to the piece size, so a v2-only single file of unaligned size is two files here, the file and its tail pad. `parse_info_section` counted the pad and called the torrent multi-file, so its `url-list` entries got a '/'. `WebPeer::new` (`num_files() == 1`) did the same again at connect time. The file was then asked for at `<url>/<name>` and got a 404 (libtorrent 2.0.11 and RC_2_0 do this too). **Fixed:** the torrent is multi-file only when its tree has more than one top-level file. `web_peer::serves_one_file` counts a file plus its tail pad as one file, both for the URL and for banning a seed that sends bad data. Recorded as a divergence in PORTING. Tests: `a_padded_v2_only_single_file_keeps_its_url_list_entry`, and `v2_only_single_file_from_its_url_list`, which still failed after the parser fix alone (two 404s at `one.bin/`) and drove the connection-side fix.
- **LSD at interval 0:** 2.1.0's millisecond spread turns `local_service_announce_interval` 0 into a 1 ms period, three multicast packets per socket every millisecond, and the Advanced page accepts 0. **Fixed:** an interval under 1 s now counts as 1 s, which is 2.0.11's floor. The read loop's `Err(_) => continue`, also named in the hunt, was already a `break`.
- **JSON `\u` escapes:** both parsers (Web UI and search helper) accepted `\u+041`, because `from_str_radix` takes a leading '+'. **Fixed:** they now require four hex digits. The other `from_str_radix` sites are client-side chunk sizes and hex test helpers; they were left as they are.
- **Hand check 26 (hidden desktop, two monitors: 3840×2160 primary, 1920×1080 at its right):** `window.rect` was set to 5000,5000,5900,5620, which lies on no monitor; the window came up at 2940,1492-3840,2112, inside the primary's work area. A 3000×4200 rectangle left of the screen came back as 0,25-3000,2112, shrunk to the work area. Hand check 30 (GTK Create's Cancel during the last piece) has still not been run.
- **Validation:** core lib 936 passed; web_seed 22 of 22; both JSON test sets; clippy `-D warnings` on the workspace clean; rustfmt clean. `PEER_ID_PREFIX` is unchanged, because nothing changed on the peer wire.
- **Changelog:** the three entries of 2026-11-11 were moved to the archive.

## 2026-11-13_210657_1794600417: Version 1.2.47: the shared part of the UI lock (D69)

- **Asked by the owner:** a PIN lock for the desktop windows, as qBittorrent's "Lock qBittorrent", so someone at the computer cannot see the torrent list; easy to reset, with a wiki page on how. Owner's answers: a PIN of 4 to 6 digits, the windows hidden in the tray, locking by hand only (the state survives restarts), reset by holding Ctrl (Windows) or Option (macOS) at start or with `--reset-lock`. Plan: this shared slice, then one slice per GUI.
- **Moved:** the PBKDF2-HMAC-SHA256 password hash, HMAC-SHA256, the constant-time compare and `random_hex` from nox's `webui::auth` to `core::crypto::password` (with their RFC tests), so the GTK and Mac GUIs, which do not link nox, can hash the PIN; `webui::auth` re-exports them.
- **New `frontend::ui_lock`:** the keys `ui.lock_pin` (a salted hash in the Web UI password's format) and `ui.locked`, outside `GuiOptions` so Preferences never writes them; PIN rules; lock, unlock and remove; `Guard` (from the fifth wrong PIN on, each one starts a 30 s wait, in memory); `Form` and `submit` for the four PIN dialogs, so each GUI only lays out boxes; `--reset-lock`; `without_lock_keys` for the Web UI a Windows window hosts. `Events::take_popups` lets the Mac hold its popups while locked.
- **Strings:** 20 new keys (menus, the prompt, the PIN dialogs, the reset question) in all 35 tables; the 34 translations are machine-made.
- **Validation:** tests on Windows: core lib (935, 4 new), frontend (390 + 4, 9 new), nox (all suites, a new hosted test that the Web UI never shows or changes the lock keys); workspace fmt and clippy clean; the GTK and Mac crates lint from Windows (stand-in pkg-config, the 1.90 toolchain's targets). No GUI uses the lock yet.
