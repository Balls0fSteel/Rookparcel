## 2026-11-18_000752_1794956872: Version 1.2.70: unreadable files stop a check, queued checks say so, round-robin connections; test flakes

- **On the owner's word** ("Engine bugs + flakes", from the BACKLOG triage).
- **A check that cannot read a file (`core::disk`):** a full check took every read error as "piece not had", so a seed whose files another program held (or without permission) came out with no pieces and downloaded everything again. Now, as libtorrent's `on_piece_hashed`, only a missing or short file means "not had"; any other read error stops the torrent with a file error. A restarting seed reaches this only when its resume data does not match (otherwise nothing is read), and a file that is not found at all still loses its pieces (1.2.46's rule), so this is one possible cause of the owner's two seeds of 2026-11-10, not a proven one (BACKLOG "Disk and storage" (a) stays open). Tests: a directory in a file's place, in the disk check and in a seed restarted with it (error; with the file back, Start finds it seeding without hashing).
- **"Queued for checking" (`TorrentStatus::check_queued`, remote `PROTOCOL` 21):** a check waiting for its drive (one per drive, D48) read "Checking 0.0 %"; the disk now reports when it takes a check up (`Completion::CheckStarted`), and all GUIs and the Web UI show it as queued (text, class, icon). The flag lives in `checked_pieces` (`CHECK_QUEUED`): `Torrent` stays at 688 bytes.
- **Connection attempts (`try_connect_more_peers`):** the tick's budget went to the torrents in slot order, each taking all it could, so a torrent late in the order could wait for peers indefinitely; now round robin, downloads first and every tenth attempt to a finished torrent, as libtorrent. A finished torrent passes over seeds before taking its best candidates (before, it took the best and then dropped the seeds, so leechers behind them waited). A torrent with no peer to try leaves the tick's round at its first miss (libtorrent's lists hold only torrents that want peers), so an idle tick asks each torrent once, as the old loop did; the idle-CPU benchmark was not rerun. Test: 60 silent peers ahead of a magnet's one seed fail the old loop and pass in 7.6 s. PORTING.md records what is not ported.
- **macOS flake of `a_download_stopped_midway_resumes_with_its_names_and_pieces`:** the figures fit one half-done piece fetched whole after the restart. Not reproduced (120 runs under load on Windows); the test now reports which way it went (the check's Logger line, bytes done after the check against before). No engine change.
- **Test flakes** (a helper agent; test code only): `proxy.rs`'s waits kept no skipped alerts, so a `TorrentFinished` before the awaited tracker reply was lost (reproduced with a slow tracker, then fixed); the Win32 helper-button test and the main window's search test share a lock (both point the process-wide search helper); the Web UI setup test compares with the port it proposed; window tests hold `util::TestWindow`, so a failing assertion no longer hangs the run. The schannel key-name flake was already fixed in `7f77205a`.
- **Validation (after the version bump):** core (982 unit and every integration suite, proxy 9), frontend 452, nox, Win32 173 (one thread); clippy `-D warnings` for core, frontend, nox and Win32, GTK (cross, stand-in pkg-config) and the Mac (aarch64); `cargo fmt --check` for the workspace and the fuzz workspace. The round-robin test was run against the old loop and fails there. Not run: GTK and the Mac on the VMs, CI.

## 2026-11-17_210056_1794945656: Version 1.2.68: the Trackers and Peers tabs sort by their headers (D78)

- **On the owner's word** ("Trackers/Peers sort", the next item after 1.2.67): no GUI sorted these tabs, Win32 included. The shared model (`Detail::sort_of` / `set_sort_of` / `toggle_sort_of` for Files, Trackers and Peers; `Core` wrappers for the Mac) uses the Files tab's three-click cycle: counts, progress, speeds and totals start descending, names, addresses, clients, flags, statuses and Update In ascending, the third click back to the engine's order. `set_peers` / `set_trackers` sort each update in place (with each row's engine position, to go back), so `peers[row]` / `trackers[row]` stay the displayed rows; every direct `detail.trackers =` became `set_trackers`. Ties go by address for peers, so equal rows do not swap every second; trackers without a reported count stay last in both directions. `row_keys` / `rows_of_keys` (a peer's address or web seed URL, a tracker's URL) keep the selection. Kept as `ui.trackers_sort`, `ui.peers_sort` (`sort_key`, `sort_from_pref_of`).
- **Win32:** header clicks on both pages, the arrow from the stored sort at start (one loop for the three sorted pages), the selection noted once per alert batch while sorted and put back without scrolling. **GTK:** `header_changed` generalises the Files mapping (tested), selection kept on updates while the tab is shown and sorted. **macOS:** the tables use the `sort_click` hook; the selection is kept by key at every refresh, sorted or not; `RPTableSource::select` now re-reads the selection when AppKit stays silent but the kept ids were stale.
- **Validation:** fmt clean; clippy `-D warnings` clean for core, frontend, nox, Win32, GTK (cross) and the Mac (both Darwin targets); tests frontend 452, Win32 173 (one thread, a new window test), Mac 24; on Xubuntu GTK 29 and frontend 451.
