## 2026-11-13_220304_1794603784: Version 1.2.50: the UI lock in the macOS app (D69)

- **Menus:** File > Lock Rookparcel (⌘L) above Close Window; Options > Lock PIN (Set, Change, Remove), greyed by whether a PIN exists; Lock without a PIN opens Set PIN first. While locked the menu bar is the app menu (Show Rookparcel, Hide, Quit) and Edit; the status item's and the Dock's menus offer Show (and Quit); unlocked with a PIN they offer Lock Rookparcel. Commands 80-83; `app::run` and `app::state` refuse what does not work locked. Built in a worktree, merged here.
- **Locking:** orders out every ordinary window and sheet, front to back, and brings the same ones back after the PIN (a minimized one leaves the Dock unseen first, so its tile cannot show the list); the main menu bar is put back as it was, not rebuilt. The prompt (`dialogs/pin.rs`) is an application-modal NSAlert with secure boxes kept to six digits by a text-field delegate. While locked, `Events::take_popups` holds errors, Add dialogs and update offers; completion notifications are dropped; torrents handed over wait for the PIN.
- **Starting locked:** the window is laid out at alpha 0 and never shown; a start by hand asks at once, `--minimized` stays in the menu bar.
- **Reset:** Option held at launch (read first thing in `main`), or `--reset-lock`; a second start forwards it in the open notification's `reset` key, and Option with a click on the Dock icon asks too. The question's buttons are Remove and Cancel (no Yes/No in the tables).
- **Validation:** 19 tests on Windows, clippy for both Mac targets and the workspace clean. On the macOS VM: lock from the menu and with ⌘L, the locked menu bar read through System Events, Show and a wrong then the right PIN, Quit while locked, a locked restart showing only the prompt, Escape, a locked `--minimized` start staying silent, opening the running app again through Finder (macOS reopens it: it comes forward and the prompt has the keyboard), `12ab34` typed as `1234`, Set PIN from Lock (Tab between the boxes; a 100,000-round hash), `--reset-lock` at start and forwarded (Remove). **Found, left:** a second copy started with `open -n` or from Terminal (only `--reset-lock` from Terminal needs one) reaches the running copy, but on macOS 15 that copy stays behind the front app, as an unlocked one did before: its question or prompt shows without the keyboard. Yielding activation to it (by bundle identifier, or to each running copy) did not change that on the VM, so nothing was kept. Quit is greyed while the PIN prompt is up (it is app-modal): Escape first.

## 2026-11-13_214927_1794602967: Version 1.2.49: the UI lock in the Windows GUI (D69)

- **Menus:** File > Lock Rookparcel (Ctrl+L) above Exit, the tray's Lock Rookparcel with a PIN set, and Options > Lock PIN (Set, Change, Remove PIN), greyed by whether a PIN exists; Lock without a PIN opens Set PIN first. Built in a worktree, merged here; the five menu items got their status-bar help texts at the merge (English; translations fall back to it).
- **Locking:** hides every captioned window of the GUI thread (main window, dialogs, message boxes, Statistics, Search Results) and brings the same ones back after the PIN, minimized ones minimized; the Auto Shutdown countdown stays. The prompt (new `dialogs::pin`, one template for the four forms, `ES_PASSWORD | ES_NUMBER`, dark-mode aware) has no owner, so it never re-enables a hidden window. Locked, the tray menu is Show and Exit and other commands do nothing.
- **While locked:** completion balloons are dropped; error boxes (at most 20), magnet Add dialogs, URL results and update boxes wait for the PIN; torrents from a second start or a double-click are held and the PIN asked for (`WM_COPYDATA` only queues, never shows a dialog inside the sender's `SendMessage`); Cancel drops them. A locked start stays in the tray and asks at once unless `--minimized`.
- **Reset:** Ctrl held (read first thing in `main`) or `--reset-lock` asks "Remove the lock PIN?" before any window; a second start forwards it in a new `WM_COPYDATA` that older builds ignore. Found and fixed by the hidden run: forwarded arguments had opened the PIN prompt while the reset question, inside its own message loop, never showed; they now wait for the answer.
- **Web UI:** the hosted Web UI starts from a copy without the lock keys, and `sync_web` / `on_web_changes` filter them out both ways.
- **Validation:** `cargo test -p rookparcel` on one thread 150 (10 new), frontend 390; workspace fmt and clippy clean. Hidden-desktop runs of a portable copy (seeded 10-round PIN): lock, a second start's prompt (a third start opens no second one), wrong PIN, the 30 s wait, Cancel, Exit while the prompt is open, locked and `--minimized` starts, `--reset-lock` at start and forwarded (Yes, No, no PIN), Set PIN from Lock; the dialogs pictured in light and dark. The held Ctrl key reads 0 on a hidden desktop, so only a unit test covers it. Left: the D47 closing window still lists moves when Exit is chosen while locked.

## 2026-11-13_214643_1794602803: Version 1.2.48: the UI lock in the GTK GUI (D69)

- **Menus:** File > Lock Rookparcel (Ctrl+L) above Exit; Options > Lock PIN with Set, Change and Remove PIN, greyed by whether a PIN is set; Lock without a PIN opens Set PIN first. The tray offers Lock Rookparcel with a PIN set, and only Show and Exit while locked (a pure `tray::visible` also drops leftover separators). Built in a worktree, merged here.
- **Locking:** every visible window but the Auto Shutdown countdown hides and comes back after the right PIN; `ui.locked` is saved at once. Showing the windows (the tray, a second start) asks in one prompt (new `lock.rs`: hidden digit-only boxes, the filter on the entry's delegate, the shared `ui_lock::submit`). While locked, message boxes, magnets' Add dialogs, downloaded torrents' dialogs and update offers wait; completion notifications are dropped; torrents from a second start wait for the PIN and are dropped on Cancel.
- **Starting locked:** the main window is never shown; a start by hand asks at once, `--minimized` stays in the tray. Without a tray (plain GNOME) the prompt stands in for the window: no Cancel, and closing it quits. Exit closes the never-shown main window by emitting `close-request` itself (`gtk_window_close` ignores unrealized windows). On the way: Minimize to tray now also works for a window first shown after the tray started.
- **Reset:** `--reset-lock` asks (Cancel/OK, as the GTK GUI's other questions; the tables have no Yes/No) before the window is built, or in the running window when another start forwards it; OK removes the PIN and logs it; with no PIN it says "No lock PIN is set."
- **Validation:** clippy for Linux from Windows (stand-in pkg-config); on the Xubuntu VM `cargo test -p rookparcel-gtk` (22, 2 new) and an Xvfb run with a private bus (no tray) and with the Xfce panel's tray under a profile: lock, the tray menus read over D-Bus (locked: Show, Exit; unlocked with a PIN: Lock above Exit), five wrong PINs then the 30 s wait, `12ab34` typed as `1234`, Ctrl+Q from the prompt, a locked restart showing only the prompt, a second start bringing the same prompt forward, Escape keeping it locked in the tray, `--reset-lock` at start (Cancel, OK, no PIN) and forwarded. The VM's own autostarted AppImage shares the default application id, so the tray run used `--profile locktest`.

## 2026-11-13_210657_1794600417: Version 1.2.47: the shared part of the UI lock (D69)

- **Asked by the owner:** a PIN lock for the desktop windows, as qBittorrent's "Lock qBittorrent", so someone at the computer cannot see the torrent list; easy to reset, with a wiki page on how. Owner's answers: a PIN of 4 to 6 digits, the windows hidden in the tray, locking by hand only (the state survives restarts), reset by holding Ctrl (Windows) or Option (macOS) at start or with `--reset-lock`. Plan: this shared slice, then one slice per GUI.
- **Moved:** the PBKDF2-HMAC-SHA256 password hash, HMAC-SHA256, the constant-time compare and `random_hex` from nox's `webui::auth` to `core::crypto::password` (with their RFC tests), so the GTK and Mac GUIs, which do not link nox, can hash the PIN; `webui::auth` re-exports them.
- **New `frontend::ui_lock`:** the keys `ui.lock_pin` (a salted hash in the Web UI password's format) and `ui.locked`, outside `GuiOptions` so Preferences never writes them; PIN rules; lock, unlock and remove; `Guard` (from the fifth wrong PIN on, each one starts a 30 s wait, in memory); `Form` and `submit` for the four PIN dialogs, so each GUI only lays out boxes; `--reset-lock`; `without_lock_keys` for the Web UI a Windows window hosts. `Events::take_popups` lets the Mac hold its popups while locked.
- **Strings:** 20 new keys (menus, the prompt, the PIN dialogs, the reset question) in all 35 tables; the 34 translations are machine-made.
- **Validation:** tests on Windows: core lib (935, 4 new), frontend (390 + 4, 9 new), nox (all suites, a new hosted test that the Web UI never shows or changes the lock keys); workspace fmt and clippy clean; the GTK and Mac crates lint from Windows (stand-in pkg-config, the 1.90 toolchain's targets). No GUI uses the lock yet.

## 2026-11-11_085623_1794383783: The nox search test no longer races the torrent list

- **Failure:** CI for `05f93fdd` (no code changed), Windows only: `sources_search_and_add` got 200 where it expects 409 for a second add of the same magnet.
- **Cause (read from the code, not reproduced here):** `/pa/search/add` answers 409 from `by_hash`, which is filled when a torrent's first status arrives. The test added a `.torrent` and a magnet, waited only for the `.torrent` to be listed, then added the magnet again; on a slow runner the magnet's status had not come yet.
- **Fix (test only, no version bump):** the test waits until both torrents are listed. `cargo test -p rookparcel-nox --test search`: 3 passed, and the test alone passed 8 more times.
- **Left:** the gap itself (PLAN "Current status"): a real second add inside it returns 200.
