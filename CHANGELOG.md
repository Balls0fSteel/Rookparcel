## 2026-11-17_210056_1794945656: Version 1.2.68: the Trackers and Peers tabs sort by their headers (D78)

- **On the owner's word** ("Trackers/Peers sort", the next item after 1.2.67): no GUI sorted these tabs, Win32 included. The shared model (`Detail::sort_of` / `set_sort_of` / `toggle_sort_of` for Files, Trackers and Peers; `Core` wrappers for the Mac) uses the Files tab's three-click cycle: counts, progress, speeds and totals start descending, names, addresses, clients, flags, statuses and Update In ascending, the third click back to the engine's order. `set_peers` / `set_trackers` sort each update in place (with each row's engine position, to go back), so `peers[row]` / `trackers[row]` stay the displayed rows; every direct `detail.trackers =` became `set_trackers`. Ties go by address for peers, so equal rows do not swap every second; trackers without a reported count stay last in both directions. `row_keys` / `rows_of_keys` (a peer's address or web seed URL, a tracker's URL) keep the selection. Kept as `ui.trackers_sort`, `ui.peers_sort` (`sort_key`, `sort_from_pref_of`).
- **Win32:** header clicks on both pages, the arrow from the stored sort at start (one loop for the three sorted pages), the selection noted once per alert batch while sorted and put back without scrolling. **GTK:** `header_changed` generalises the Files mapping (tested), selection kept on updates while the tab is shown and sorted. **macOS:** the tables use the `sort_click` hook; the selection is kept by key at every refresh, sorted or not; `RPTableSource::select` now re-reads the selection when AppKit stays silent but the kept ids were stale.
- **Validation:** fmt clean; clippy `-D warnings` clean for core, frontend, nox, Win32, GTK (cross) and the Mac (both Darwin targets); tests frontend 452, Win32 173 (one thread, a new window test), Mac 24; on Xubuntu GTK 29 and frontend 451. Live: Win32 picture on the hidden desktop, GTK under Xvfb against a mock nox, the Mac app on the VM (BACKLOG "Trackers and Peers tab sort").

## 2026-11-17_194447_1794941087: Release workflow: the Flatpak runtimes copied into the container's own layer

- **Problem:** the v1.2.67 Release run built ten of eleven jobs; `flatpak (x86_64)` failed three times in a row (two re-runs), each on runner image `ubuntu24/20261111.127`: every runtime update in the builder container failed with "Invalid cross-device link", the GNOME SDK's too, and flatpak-builder exited. 1.2.65's run that morning (image `.370`) and the aarch64 leg passed with the same container digest and cache.
- **Found with a probe branch** (`ubuntu-24.04`, the same container, deleted afterwards): the runtimes are installed in the image's layers at `/var/lib/flatpak` (3.9 GB) and the container's overlay has no `redirect_dir`, so flatpak cannot rename their directories; `flatpak --system update` failed with EXDEV, and after copying the installation into the container's own layer (25 s) the same update succeeded.
- **Fix:** the `flatpak` job copies the installation before flatpak-builder (both legs, skipped if it is a mount point); RELEASING.md "Flatpak" says why. No program changed, so the version stays 1.2.67; the unpublished tag `v1.2.67` moves to this commit (no draft had been made).

## 2026-11-17_183218_1794936738: Version 1.2.66: the GTK and macOS Files tabs sort by their headers (D78)

- **On the owner's word** ("do the Linux/Mac sort job"): both GUIs now call the shared model Win32 uses. `Core::set_file_sort` and `Core::toggle_file_sort` are new (they flag the detail event) for the Mac, which holds `Core`, not a `Detail`.
- **GTK:** the `ColumnView`'s columns get sorters that never reorder (the model sorts); a header change becomes the next step of the cycle (`files_header_changed`, tested), so GTK's own two-state toggle cannot disagree with the model, and the header shows the model's sort (cleared on the third click). The selection is taken as `file_marks` before a sort, a new file list or a progress update of a sorted Done/% column, and put back by `file_rows_of` after.

The tree keeps its selection by node and reloads when `Detail::file_order` changes; the plain list keeps its selection's marks from each selection change and reselects after a re-sort, without scrolling. The stored sort is read before the tab is built.
- **Validation:** fmt clean; clippy `-D warnings` clean for core, frontend, nox and Win32, GTK (cross, stand-in pkg-config) and the Mac (x86_64 and aarch64 Darwin); frontend 451 tests. On the VMs: GTK built, its 28 tests and the frontend's passed, and the Xvfb run checked the cycle, the selection and the restart; the Mac app built and signed, 24 tests, and an Accessibility-driven run checked the same. ## 2026-11-17_092503_1794903903: Version 1.2.64: peers again after a file is turned on; Files tab sort; a visible unfocused selection (D78)

- **"Downloading" with no peers after turning a file on (owner):** two delays, both reproduced. The seeds `on_finished` closed as redundant were stamped as just connected, so each waited out `min_reconnect_time` (60 s, longer after failures) before it was a candidate again; libtorrent 2.0's `resume_download` has the same gap. And nothing re-announced: the next tracker announce could be an interval (about 30 min) away, asked with `numwant` 0 when the torrent had many peers. A theory that trackers saw left=0 was ruled out (a skipped file keeps left above 0). New `Engine::resume_download` for the finished-to-downloading change: reaps pending closes, forgets every known peer's last connection (as on leaving upload mode), asks each tracker again as soon as its `min interval` allows (`TrackerEntry::announce_soon`, not for failing or busy trackers; event none), prompts the DHT and LSD and connects at once. A stopped torrent that becomes unfinished now asks for an auto-manage pass. New swarm tests (reconnect with a 3,600 s reconnect delay; a re-announce with left>0 that finds a seed only the tracker knows) failed before and pass; the old skip test lost its second-seed workaround. Wire format unchanged, so `PEER_ID_PREFIX` stays. Still as in libtorrent: Force Re-Check and pause/resume leave peers in the 60 s delay.
- **Files tab sort (Win32, owner):** header clicks sort by any column (names, sizes and pieces ascending first; Done, % and Priority descending first), a second click reverses, a third returns to the torrent's order; the tree sorts each folder, folders first; kept as `ui.files_sort`. Rows moved by progress or priorities keep their selection. The owner's offer of a limit or a progress dialog was measured away: 100,000 files sort in 1-66 ms in a release build (`sorting_a_hundred_thousand_files`, ignored by default). GTK and macOS sort no detail table yet (BACKLOG); the Web UI already sorted Files.
- **Unfocused selection (Win32, owner):** after Alt+Tab a selected row was drawn in the button face (0xF0F0F0), one step from the shaded rows (0xEFEFEF), so it vanished on them. Now the highlight mixed into the window colour (30 % light, 70 % dark) under the window's text; High Contrast keeps the highlight. Pictured light and dark on the hidden desktop.
- **Validation:** frontend 451 tests, Win32 172 (one thread), core lib and every core test binary (swarm 62), clippy and rustfmt clean on the changed crates.
