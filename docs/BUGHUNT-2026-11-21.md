# Bug hunt, 2026-11-21

Timestamp: 2026-11-21_002110_1795216870. Tree: `13d405d0` (1.2.70, not released). A read-only review by eighteen parallel reviewers (fifteen Sonnet, three Haiku), one per area, sized by lines: the engine in four slices, disk, metainfo, net, uTP and DHT, proto/remote/crypto, nox's Rust side, the Web UI's `app.js`, the frontend crate, Win32 in two slices, GTK in two, macOS, and a sweep of casts and arithmetic on wire- and file-derived values. Each was told the 2026-11-05 hunt, BACKLOG and SECURITY-REVIEW.md, and to compare with libtorrent 2.0.11 where the port diverges. The briefs named SECURITY-REVIEW.md at the root, so several reviewers missed `docs/SECURITY-REVIEW.md`; the eleven high and medium findings were then searched for in it, SECURITY-AUDIT.md, PORTING.md, DECISIONS.md and WEBUI.md, and none is listed or documented as intended there. Nothing was built, run or fixed. Line numbers are those of `13d405d0`.

Legend: **traced** = re-read at the cited lines in this session and the path holds; **plausible** = the code is as described, but the trigger rests on the reviewer's trace or on platform behaviour not checked here. Two reviewers found 2 independently.

## High

1. **Piece layers shipped in a .torrent are never checked against the file roots** (`crates/core/src/metainfo/torrent_info.rs:552-587` `parse_piece_layers`; `crates/core/src/engine/v2.rs:80-84` `build_trees`; `torrent_info.rs:936-948` `v2_piece_hash`; `crates/core/src/disk/mod.rs:1421-1433` `PieceHasher::verdict`; traced). `parse_piece_layers` checks only the keys and the lengths, although its doc says the hashes are verified "when the torrent is loaded". `build_trees` does `let _ = tree.load_piece_layer(layer)` and drops the failure, and the disk hasher's verdict compares each piece's merkle root with `TorrentInfo::v2_piece_hash`, which reads the unverified layer (PORTING.md "v2 piece verification" describes that comparison, not a check of the layer). `v2_piece_layers_complete` is true for the forged layer, so `start_torrent` (`engine/mod.rs:2651`) fetches no layers either. `piece layers` sits outside the info dict, so a forged layer keeps the info-hash. A v2-only torrent then accepts data that matches the forged layer under the genuine `btmh`, and nothing compares the data with `pieces root`. A hybrid gets an inconsistent v1/v2 verdict on every piece, so it never completes. Layers loaded from the store (`set_piece_layers`) take the same path. libtorrent `torrent::initialize_merkle_trees` (`torrent.cpp:7681`) fails the torrent with `torrent_invalid_piece_layer`. The test with `v2_piece_layer_invalid_file_hash.torrent` (`torrent_info.rs:1570`) passes only because of the `Ok(_) if expected == TorrentInvalidPieceLayer` arm at `:1592`. Fix: verify each layer against its root in `parse_piece_layers` (what `MerkleTree::load_piece_layer` does), or fail the torrent in `build_trees`.

2. **`/pa/remote` still bypasses `--webui-save-root` three ways** (`crates/core/src/remote/mod.rs:207-254` `dispatch`; `crates/core/src/engine/mod.rs:2007-2011`, `:2029`; traced; found by two reviewers). The 1.1.69 fix for 2026-11-05 item 5 checks only `AddTorrent.save_path` and `MoveStorage`. (a) An `AddTorrent` with `TorrentSource::Resume` passes the check on `p.save_path`, then the engine replaces it with the resume record's `save_path`. (b) `RenameFile` falls into the `cmd =>` arm, and the disk layer accepts an absolute name or joins `..` onto the save path (`disk/mod.rs` ~2596-2600). (c) `AddTorrentParams.renamed_files` is never checked and is applied at `:2029`. The Web UI refuses the same names in `valid_new_path` (`nox/src/webui/commands.rs:932-951`). A logged-in remote client is needed. Fix: refuse Resume sources from remote, or check the decoded record's save path; run `RenameFile` names and `renamed_files` values through `valid_new_path` and the policy.

## Medium

3. **Turning the DHT on or off in a running session does nothing** (`crates/core/src/engine/mod.rs:1832-1917` `apply_settings`, `:734`; `engine/dht.rs:137`, `:172-184`, `:444`; `engine/listen.rs:130-136`; traced). `start_dht` runs once, at session start. `apply_settings` handles `enable_lsd`, `enable_natpmp` and `enable_upnp` changes but not `enable_dht`, and `should_announce_dht` checks only the torrent's `DISABLE_DHT` flag. Switched off, the node keeps running, announcing and adding peers until restart. Switched on after starting with it off, it never starts: the UDP sockets reopen only when the UDP wish changes, which uTP (on by default) keeps true, and `dht_socket_opened` has nothing waiting. The preferences send it to `apply_settings` with no restart note (`pref_pages` has none; the macOS window applies each control at once, D61). This answers BACKLOG "Engine networking" "Check DHT disable/re-enable on a live session" (`BACKLOG.md:737-738`). Fix: start or stop the DHT in `apply_settings`, as libtorrent's `update_dht` does; keep the state dir in the engine and clear `pending_routers` on stop.

4. **A tracker reply that arrives after the torrent stopped blocks the next start's announce** (`engine/mod.rs:3546-3592` `apply_tracker_results`, `:2753-2779` `stop_torrent`; `engine/tracker.rs:185`, `:211-221`; traced). `start_sent` is set when the reply arrives, so a pause during a slow `started` announce sends no `stopped`, and `reset()` clears the run. The late reply is still applied: `start_sent = true`, `next_announce = now + interval`. `start_torrent` (`:2619`) does not reset the trackers, so on resume no announce goes out for up to the interval (often 30 min), so no tracker peers, and the later one carries no `started` event. A late failure sets a back-off on a stopped torrent. `apply_tracker_results` checks only that the torrent and URL exist. libtorrent aborts the requests when it stops announcing. Fix: drop results for a torrent that is not active, or tag jobs with a per-torrent stop generation.

5. **A banned peer is accepted again when it connects in** (`crates/core/src/engine/pe.rs:102-131` `attach_incoming`; `engine/peer_list.rs` `connecting` ~547-556; traced). `attach_incoming` checks accept, duplicate address, the connection limit and the IP filter, never `banned`, and bans are keyed by ip:port. A peer smart-banned for corrupt data reconnects from another source port, gets a new unbanned `KnownPeer` and sends bad data again; `banned` is only read to skip outbound candidates and in eviction. libtorrent's `peer_list::new_connection` looks peers up by IP (with `allow_multiple_connections_per_ip` off, the default) and refuses a banned one. Fix: refuse an incoming connection from an IP with a banned entry; ban by IP and close every connection from it.

6. **`Reach::for_links_from` decides with its own DNS lookup and `any`** (`crates/core/src/net/fetch.rs:102-110`; callers `frontend/src/rss/worker.rs:76`, `frontend/src/search/worker.rs:41`; traced). A feed host whose DNS answers with a public and a private address (or rebinds) gets `Reach::User`, so every item link from that feed may go to loopback or the LAN, which SEC-26 is meant to stop. `proxy_for` uses the same test, so such a host also skips the proxy. The lookup goes to the local resolver even when a proxy resolves names (`proxy_hostnames`), leaking the host name. Fix: take the reach from the address the page fetch actually connected to; at least use `all`, and treat the host as public when the proxy resolves names.

7. **End-game duplicates blocks too early and too many at once** (`crates/core/src/engine/picker.rs:326-355`; caller `engine/wire.rs:655-682`; traced against `request_blocks.cpp:200-230`). Step 3 runs whenever this peer has no free block it can take, even while unstarted pieces remain and with its queue non-empty (`request_blocks` only tops the queue up to `desired`), and takes up to `num_blocks` busy blocks. libtorrent sets `dont_pick_busy_blocks` under `strict_end_game_mode` (on by default; the port has no such setting) while the download queue is shorter than the pieces still wanted, and whenever the peer already has requests out, and then takes one busy block. With partial peers (one that has only pieces others are fetching) this wastes bandwidth mid-download; `MAX_ENDGAME_REQUESTS` caps it at two requesters per block. `in_endgame()` (`:467`) exists but `pick` does not use it. Fix: allow busy blocks only in end-game proper and for a peer with an empty queue, one at a time.

8. **An RSS smart filter loses an episode for good when its download fails** (`crates/frontend/src/rss/mod.rs:540-546` `forget`, `process` ~427-470; `rss/worker.rs:9`; traced). The episode is recorded in `seen_episodes` / `episodes` before the `.torrent` is fetched; `forget` clears only `downloaded`, and says so ("Episodes the smart filters recorded stay recorded"). After a timeout, a 5xx or a login page, the next refresh skips the item as a duplicate episode, although `worker.rs:9` promises it "is tried again at the next refresh". `last_match` likewise holds the filter's minimum interval after a failed add. The tests use titles without an episode. Design call: record episodes only once the add succeeds, or have `forget` undo the keys and `last_match` it recorded.

9. **A late DNS answer for a timed-out HTTP tracker request steers another request** (`engine/tracker.rs:1198-1207` `tick`, `:1179-1195` `on_resolved`, `:767` `http_resolved`; traced). The timeout removes the connection but leaves `waiting[cookie] = Http(slot)`; the slab reuses the slot; when the old lookup returns, `http_resolved` reconnects the new job (another tracker's URL, perhaps with a passkey) to the old host's addresses. Needs a lookup slower than the 30 s timeout, which two resolver threads stuck on dead tracker hosts can produce. UDP is safe (random transaction ids). Fix: drop the `waiting` entries of a removed slot, or keep the cookie in the connection and compare.

10. **A failed append to `resume.log` is retried after the torn bytes** (`crates/core/src/store.rs:435-449` `flush`; replay `:508-540`, `:225-229`; traced). On ENOSPC or a short write, `flush` returns with `pending` kept and the file not cut back to `log_len`; the next save appends everything again after the torn entry. At the next start `replay_log` (`:508-540`) either stops at the torn entry, and `read_records` (`:225-228`) cuts the log there, losing every record the successful retry wrote; or, when the torn entry's header is whole, its length runs into the retried copy, so a corrupt record replaces that torrent's good one and the replay stops a little later. A torrent whose record fails to decode is left out of the next `resume.db` write and disappears. Fix: `set_len(log_len)` on any error, or write at `log_len` instead of appending.

11. **Unbanned guessing of the current password from a bypass session** (`crates/nox/src/webui/prefs.rs:1978-1986`; `webui/search.rs:206-217`; traced). A wrong `webui.current_password` only removes the session, and the bypass pseudo-sessions (`local`, `subnet`, `apikey`) are recreated on the next request; `bans.failed` is not called. A local user, a whitelisted host or an API-key holder can guess without limit the password that guards Run Program and the login settings; each PBKDF2 verify runs under the State lock. Fix: count wrong tries in `bans` and refuse when banned; verify outside the lock.

## Low

12. **Win32 Preferences: a Web UI that fails to start refuses every other change** (`crates/win32/src/preferences.rs:2386-2392` `apply`, `:2038-2090`, `:2095-2117`; plausible). A `Failed` Web UI status never counts as running, so each OK or Apply retries it; when it fails again `apply` returns before `hooks.apply`, nothing is stored and OK does not close, while `apply_integration` has already written the registry. Fix: apply the other settings before the Web UI restart, or close after showing its error once.

13. **A full peer list evicts banned peers first, which lifts the ban** (`engine/peer_list.rs:471-486` `evict_one`; traced). `max_by_key((banned, failcount, rank))` picks banned entries before anything else; a new PEX or tracker peer can then re-add the address unbanned. It also evicts healthy candidates where libtorrent's `is_erase_candidate` would reject the new peer.

14. **Parole: pad and restored blocks break "exclusive"** (`engine/picker.rs:49-51` `exclusive_to`; traced). A `Finished` block with no peer (pad blocks, blocks restored from resume data) is neither `Free` nor the peer's, so no peer is exclusive to such a piece. A peer on parole starts it, cannot continue it on its next top-up and starts another piece, and the rest goes to other peers, so a second hash failure is not pinned on it. Fix: treat `Finished` blocks with no peer as neutral.

15. **Hybrid torrents: v2 trackers are not nudged to send `completed`** (`engine/mod.rs:3038-3044` `on_finished`; traced). The loop clears `next_announce` for `t.trackers` only, so the v2-hash announces wait for their interval. libtorrent's `finished()` nudges every tracker.

16. **UPnP: a disabled device keeps global mapping slots in use** (`engine/upnp.rs:331-350` `delete_mapping`, unmap reply ~1012-1060; plausible, perhaps inherited). `delete_mapping` skips disabled devices, so their `protocol` stays set and the slot (50 in all) is freed only when every device's is clear. A device disabled after a failed add (`:918`) leaks two slots per listen-port remap; after about 25 remaps "too many mappings" stops UPnP until the mapper restarts. Compare `upnp.cpp delete_mapping` before fixing.

17. **A stale `CheckProgress` overwrites "Queued for checking"** (`engine/mod.rs:3417-3423`; traced). Unlike `CheckStarted` (`:3425`) and `Checked` (`:3436`), it does not check that the storage is the torrent's current one. Stop and start during a check: the old storage's progress writes over `CHECK_QUEUED`, so the row shows "Checking N %" and the percentage jumps. Display only; whether a released check still reports was not traced.

18. **Web UI: a session expiry under an open dialog leaves the login unusable** (`crates/nox/src/webui/app.js:5467-5476` `showLogin`; `page.html:94-372`; traced). The `<dialog>`s are siblings of `#app`, opened with `showModal`, and `showLogin` hides `#app` without closing them; the modal makes the login form inert until the user cancels. Fix: close `dialog[open]` in `showLogin` (as `:1764` already selects them).

19. **`sync/torrentPeers` indexes a torrent that may be gone** (`crates/nox/src/webui/api.rs:1534`; traced). `st.torrents[&id]` runs after `query` released the lock; a torrent removed meanwhile (an *arr app deleting it while a UI polls peers) panics the connection thread. Fix: `get` and 404.

20. **A stray `Authorization: Bearer` on a valid session counts as failed logins** (`webui/api.rs` ~280-310 `verify_api_key`; plausible). With the API key on, a front proxy that forwards another bearer token gets the address banned after `max_auth_fail_count` requests, although its SID is valid.

21. **Win32: one profile's association change strips another profile's Default apps entry** (`crates/win32/src/integration.rs:388-415`; plausible). `write` builds `Capabilities` from the current profile's wishes only, so profile B ticking only .torrent deletes the magnet capability the default profile still owns, and B unticking everything removes the whole entry while magnet is still registered to A.

22. **Run Program's shell guard misses wrappers and interpreters** (`crates/core/src/run_program.rs:136-201` `shell_reads_codes`; plausible). `env sh -c "... %N"`, `busybox sh`, `wsl bash -c`, `ssh host "..."`, `python -c`, `osascript -e` pass, and a torrent name such as `x$(calc)` is re-parsed by the inner shell. A heuristic gap; at least a docs line, or refuse a placeholder after any `-c` / `-e` / `/c` argument.

23. **RSS: editing a feed's URL during its fetch applies the old URL's items** (`frontend/src/rss/mod.rs` `edit_feed` ~275, `feed_fetched` ~349; plausible). `busy` is keyed by feed id; nothing checks the URL when the result lands, so the feed's filters run on the old feed's items. Fix: carry the URL or a generation in the result.

24. **RSS: the "Show - NN" fallback reads version numbers as episodes** (`frontend/src/rss/episode.rs` ~150-175; plausible). "Ubuntu - 22.04" and "Ubuntu - 22.10" both become episode 22, so a smart filter drops the second. Fix: reject a number followed by `.` and a digit.

25. **GTK: child-window dialogs appear while the UI is locked** (`crates/gtk/src/create.rs:273-276`, `search_helper.rs:118`, `:186-190`; plausible). Create's error box and the search helper's messages, `present` and site picker after an `await` bypass `when_unlocked`; one message shows the Jackett password. Whether a dialog with an unmapped parent appears depends on the desktop.

26. **GTK Search: the source dropdown changes source after Manage Sources** (`gtk/src/search.rs` `sources_changed` ~372, `fill_sources` ~514; plausible). The window keeps `Mode::Source(index)`; removing a source above it selects the next one or falls back to All. `remap` is applied only to the toolbar mode.

27. **GTK: the tray leaving while locked leaves nothing on screen** (`gtk/src/app.rs:1816-1825`; plausible). With the windows locked or hidden in the tray and no PIN prompt, a StatusNotifierWatcher restart calls `shown(false)`, which only moves an existing prompt. Starting Rookparcel again recovers. Fix: ask for the PIN, or show the window, when the tray goes away.

28. **macOS Manage Sources: a stale selection after Remove** (`crates/cocoa/src/search/sources.rs` `ask_remove` ~290; `table.rs:621-641` `reload_keep_selection`, `:184`; plausible). The flat `rows_of` has no bound, so removing the last row passes an index past the end to `selectRowIndexes`; whether AppKit raises was not checked. Fix: keep only ids below `numberOfRows`.

29. **Trackers tab: a URL listed twice keeps the selection on its first copy** (`frontend/src/detail.rs` `rows_of_keys` ~398-411; plausible). Rows are keyed by URL alone, so with two equal URLs each refresh re-selects the first. Not confirmed that duplicates reach the tab (`engine/mod.rs:2003-2004` pushes extra trackers without a dedup).

30. **Win32: posted messages carry raw pointers from anyone** (`crates/win32/src/app.rs:3786-3787`, `:3835-3836`, `:3839-3849`; plausible, hardening). Any same-user process can post `WM_APP_URL` / `WM_APP_UPDATE` with a bogus `lparam` (`Box::from_raw`) or `WM_APP_WEBUI` with an unknown `wparam`, which quits. Fix: pass ids, and match the shutdown code explicitly.

31. **Win32: a second start's arguments are dropped during the close** (`win32/src/app.rs:4070-4073`, `main.rs:207-234`; plausible). After `APP` is taken, `with_app` returns `None` but the handler still returns 1, so the sender reports the hand-over as taken and the magnet or file is lost. Narrow window. Fix: return 0 without the app, or park the arguments in a static as the waiting window does.

32. **Web UI: the selection keeps removed torrents** (`app.js` ~145-146, ~567-597; plausible, cosmetic). Torrents removed elsewhere stay in `sel`, so "N selected" and "Remove N torrents?" count them; the server ignores unknown ids.

33. **`remove_tail_padding` leaves `mtime` and `roots` unshifted** (`metainfo/file_storage.rs:432-448`; plausible). For a hybrid from libtorrent 2.0.0-2.0.7, an empty file after the removed pad reads its neighbour's mtime.

34. **Secure Transport counts a close without `close_notify` as clean** (`core/src/net/tls/secure_transport.rs` `process`; plausible, latent). `ERR_SSL_CLOSED_NO_NOTIFY` sets `closed`, which `closed_cleanly` feeds to the SEC-07 truncation check (`fetch.rs:668`). Not reachable today: the read callback never reports end of stream.

## Inherited and minor

- DHT: a ping or announce that gets no answer calls `node_failed` on every short-timeout tick (about 14 times before the 15 s timeout), because `FLAG_SHORT_TIMEOUT` is set only after the `results.is_empty()` return (`dht/node.rs:790-810`, `:1122`). Same in libtorrent 2.0.11 (`traversal_algorithm.cpp:353-378`).
- `remote/mod.rs` pump: every command `encode_command` rejects logs "the IP filter is the server's", including `SetExtraTrackers`, `PeerClass` and `GetMetadata`.
- `proto/web_peer.rs:362`, `:408`: `start + length - 1` would underflow for a zero-length request; only our own picker builds those, and none is zero.

## Looked at and found sound

The reviewers found these sound; this session did not re-read them. uTP (wraparound, SACK, LEDBAT, FIN/RESET, MTU probing) and the DHT node, routing table, tokens and traversals all match libtorrent. The disk layer's writes, pad and part files, `.!ut` renames, moves and the 1.2.70 check error path; peer-wire, v2 hash-request, ut_metadata and web-seed bounds; Web UI escaping (no `innerHTML` anywhere); the frontend model, D78 sorting, importers and preferences ranges; Win32 and GTK `RefCell` re-entry (`with_app` uses `try_borrow_mut`); TLS verification on all three back ends.
