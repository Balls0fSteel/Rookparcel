2 entries moved verbatim from the root changelog on 2026-11-10_094303_1794300183 to keep it under budget: the benchmark run of 1.2.29 with its regression, and version 1.2.30, which found and fixed it. Links and paths keep their original repository-root context.

## 2026-11-10_063403_1794288843: Version 1.2.30: the idle CPU regression of the 1.2.29 benchmarks found and fixed

- **Cause 1, the daemon's 0.33% with 10,000 torrents:** since 1.1.78 the Web UI asked the engine for every restored torrent's metadata after each start (128 per status tick) to learn its private flag; each answer read and parsed the info dictionary from the pack, about 1.2% of a core for 78 s, and the benchmark's idle window caught its end. Narrowed by running six releases side by side (1.1.40 0.10%, 1.2.0 0.32%), then per-thread CPU and `strace` on the VM. **Fix:** the engine keeps the flag: `Torrent::private`, `TorrentStatus::private` (`Option<bool>`), `lt-private` in resume data; **remote protocol 17**. The Web UI takes the list's `private` from the status and queues only torrents whose status does not say (records older than 1.2.30); `GetMetadata` stores the answer for those, so the pass runs once after an upgrade and never again (checked on 1.2.29's records: first start with the pass, second without).
- **Cause 2, the Win32 process at 100,000 (0.8-1.0%):** `lsd_tick` counted the running torrents on every engine tick by walking every slot (since 2026-10-30). `perf` on the VM with 100,000 stopped torrents: 66% of the engine thread's idle time. **Fix:** `lsd_running` walks `live` (the active torrents).
- **Measured:** `rookparcel-nox`, 10,000 torrents, three rounds on the VM: 0.12% after a restart (1.0.1 0.10%, 1.2.29 0.33%; `docs/benchmarks/2026-11-10-ubuntu-vm-idle-fix-1.2.30.jsonl`); 100,000 stopped torrents: the engine thread 1 clock tick in 30 s, from 23. Win32 at 100,000, two runs: process 0.36-0.39% (1.2.29 0.81-0.96%). BENCHMARKS.md "The idle CPU regression".
- **Validation:** core 924, frontend 364, Win32 122, nox 84 + 40 + 44 and the integration suites green; clippy `-D warnings` and fmt clean for the workspace; new test `the_private_flag_outlives_the_metadata`, the Web UI's queue test extended.
- **Site:** the benchmark page's "Since 1.0.1" text names the cause and the fix instead of "not explained"; its tables stay those of 1.2.29. Not done: a full benchmark run of 1.2.30.

## 2026-11-10_030501_1794276301: Benchmarks of 1.2.29: the daemon comparison rerun with old releases as controls, the engine and the GUIs; one regression found

- **Harness (`tools/bench`):** `bench.py --rookparcel PATH` (the binary was a hardcoded 1.0.1 path that no longer existed), `--control LABEL=PATH` (older releases as `rookparcel@LABEL` in the same rounds), `many --runs N`. `summarize.py`: medians over the many-torrents runs, "median of N" from the data, `--versions`, a `bench:table-versions` block for the site, and the October files' `patorrent` rows read again. Fixed on the way: a downloader whose port the tracker had not shown yet was never counted (Transmission sat out the 30-minute timeout in the smoke run); a download the client calls complete with no bytes counted now fails after 5 s with the ports.
- **Daemon run** (Xubuntu VM back at 8 GB, 2026-11-09 22:15 to 02:32, published binaries checked against `SHA256SUMS`; `docs/benchmarks/2026-11-09-ubuntu-vm-1.2.29.jsonl`): 1.2.29 equals 1.0.1 and 1.1.40 in download speed (3,154 MiB/s, 0.99 CPU s/GiB), add, start and memory after adding; 67 MB after a restart with 10,000 torrents (1.0.1: 60, the update check). The other clients measure as on 2026-10-27. Deluge failed three transfer runs (cause not found); five more passed and are in the file as runs 6-10.
- **Regression found:** idle CPU with 10,000 torrents 0.33% of a core (1.0.1 0.07%, 1.1.40 0.10%, ranges apart); the Win32 process idles about three times 1.0.1's at 100,000. Not in `lt-swarm` alone. Not fixed here: BACKLOG "Validation and development environment".
- **Engine and GUIs on this PC and the Mac VM** (BENCHMARKS.md "Engine and GUIs"): `lt-swarm` unchanged against a 1.0.1 build; the Win32 GUI at 100,000 lists in 1.37 s (1.0.1 today: 1.27 s), sorts by name faster (32-36 ms against 49-53), uses 15 MB more; the Mac GUI lists 100,000 demo torrents in 0.54-0.57 s, 191 MB.
- **Site and docs:** `site/benchmarks.html` filled from the new file, its prose checked against it (idle CPU no longer "the least"), a "Since 1.0.1" section; the home page says "under a second and a half" and "under 0.2 %" for the Windows GUI; BENCHMARKS.md has the new results, the method changes and the run's duration. No news entry (the site's tests take release entries only) and no version bump (tools, docs and site). Committed locally; the push to `main`, which deploys the site, waits for the owner.
