Benchmarks

Rookparcel's daemon beside qBittorrent, Transmission, Deluge and rTorrent: the same machine, the same torrents, every client at its own defaults. The harness, the method and the raw numbers are public, so you can run it yourself.

In short

  • A big library stays small. With 10,000 torrents Rookparcel used 68 MB after a restart, a ninth of qBittorrent's 612 MB, and listed all of them 0.22 s after it started (qBittorrent 1.62 s). Right after adding them it used 310 MB, about as much as Transmission: Rookparcel keeps a torrent's metadata in memory only while the torrent is active, and the next start leaves out the rest.
  • Fast and frugal with one peer. Downloading 2 GiB from one peer on the same machine, Rookparcel reached a median 1,469 MiB/s, the fastest of the five, and used 1.80 seconds of CPU per GiB, the least: about three quarters of qBittorrent's 2.46 s and Deluge's 2.45 s. rTorrent (2.05 s) slowed down near the end of every download.
  • Quiet when idle. Every client stayed under 2.2% of one core with 10,000 torrents; Rookparcel used the least (0.03%), then qBittorrent (0.05%). With 1,000 torrents every client was at 0.15% or less.
  • Adding is slower than it was. Adding 10,000 torrents took Rookparcel 5.4 s, against qBittorrent's 2.0 s. Releases up to 1.2.46 needed 1.85 s on the same server; the history below shows where it changed, and we are looking into it.

One rented server, measured on 22 and 23 November 2026. These numbers come from one cloud server and one kind of test each. They show what each program's code costs, not how fast your downloads will be: on the internet your connection and the swarm decide that. Read how they were measured and their limits before quoting them.

10,000 torrents

Every client got the same 10,000 generated torrents (10 MB to 20 GB, about 1,500 pieces each, three in five with several files), added started, with no data on disk and a tracker that refuses connections. Memory is the resident memory (RSS) of the client's processes after 60 seconds of settling. Every client did this three times; the medians are shown.

Then each client was stopped and started again; the time is from starting the program until its API lists all 10,000 torrents.

All the numbers

Add is from the first add request until all are listed, through each client's own API (Deluge's daemon takes them in batches of 100 over its RPC). PSS divides shared libraries among the processes using them. Idle CPU is 60 seconds without any API call, as a percentage of one core. Empty is the client with no torrents.

Downloading

One 2 GiB file of random data, seeded by a reference qBittorrent on the same machine, downloaded five times by each client with a fresh profile. Speed and CPU time are taken between 10% and 80% of the file, from the kernel's own byte counts; every downloaded file was checked against the original.

Transmission held 62.3 to 62.5 MiB/s in every run, which looks like the limit of how many requests it keeps open to a single peer rather than of its engine; with many peers it spreads out. rTorrent's downloads took about two minutes from the first byte to the last: in earlier runs it was fast until about 1.7 GiB and then flushed its memory-mapped pieces slowly. One of its five runs failed, because its API did not answer within 120 seconds, so its figures are from four.

Downloading and starting are unchanged across all six. Memory grew by about 6 MB with the update check that rookparcel-nox has made since 1.1.17 (one HTTPS request shortly after it starts). Idle CPU with 10,000 torrents had risen to 0.22% of one core in 1.2.29: after every start the daemon read each torrent's metadata once more, and local peer discovery walked the whole list on every tick. 1.2.30 removed both, and every release since uses 0.03%.

Adding got slower between 1.2.46 and 1.2.69: 10,000 torrents went from 1.85 s to 5.26 s, and 1,000 from 0.19 s to 0.56 s. 1.2.76 is the same as 1.2.69. We have not found the cause yet; the releases in between will narrow it down, and this page will say when it is fixed.

How it was measured

  • Machine: a rented Hetzner Cloud CCX23 server: 4 dedicated vCPUs of an AMD EPYC (Milan) with SHA extensions and 16 GB of RAM, running Hetzner's Ubuntu 26.04.1 image. The run took 5 hours 15 minutes.
  • Clients: Rookparcel 1.2.76 and the earlier releases 1.2.69, 1.2.46, 1.2.29, 1.1.40 and 1.0.1, the published Linux releases, each checked against its SHA256SUMS; qBittorrent 5.1.4, Transmission 4.1.1, Deluge 2.2.1 (libtorrent 2.0.12) and rTorrent 0.9.8 (libtorrent 0.13.8), Ubuntu's own packages. All ran as headless daemons.
  • Settings: a fresh profile each time, DHT, local peer discovery, peer exchange and port mapping off so no outside peer takes part, everything else at each client's defaults (queueing, caches, connection limits, encryption). Nothing was tuned for Rookparcel.
  • CPU time is user plus system time of all the client's threads, from /proc. Data for the downloads lived on a RAM disk, so no hard disk was measured.
  • Transmission is confined by Ubuntu's AppArmor profile to its service user's folders, so it ran as that user, as the packaged service does.

The harness is tools/bench (Python, standard library), the full method and how to run it again are in BENCHMARKS.md, and every run's raw results, with per-thread CPU and a trace of each download, are in docs/benchmarks. If you get different numbers, please tell us.

Limits

  • A cloud server is a virtual machine on shared hardware: its vCPUs are its own, but memory and caches are not. The downloads were repeated five times in a changing order and the medians are shown; single runs varied. The first download of a session is slow for whichever client makes it: Rookparcel 1.2.76's ran at 1,007 MiB/s against a median of 1,469, as on earlier machines. The median is not moved by that run.
  • Rookparcel hashes pieces with the CPU's SHA extensions when it has them. On a server without them (an Intel Xeon Platinum 8280, on 18 November) its download used about twice the CPU per GiB of the other clients, so on older CPUs expect the reverse of the chart above.
  • Two programs on one machine have no latency, no packet loss and no swarm. The downloads show the cost of each client's code, not internet speeds.
  • The seed took TCP only, so that every client used the same transport. Clients that try uTP first waited for that attempt to fail before they connected; that wait is left out of the comparison.
  • The 10,000 torrents had no data and no reachable tracker, so the clients held them without transferring anything. Each client's defaults decide how many of them are active at once.
  • rTorrent 0.9.8 is the version Ubuntu ships; newer rTorrent releases exist. The GUIs (Rookparcel's Windows and GTK programs, qBittorrent's desktop app) were not measured here.
